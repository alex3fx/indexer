### Перезапустить узел (смена бинаря/конфига/потеря процесса)

### Backfill найденных пропусков
1. `find_missing_blocks.py FROM TO ... > missing.txt` → получить список номеров
2. Сгруппировать в диапазоны (gap_threshold ~2000), записать в `spans.txt` как `"FROM TO"` построчно
3. `tools/backfill_spans.sh <node> <rpc_url> spans.txt backfill.log <FETCH_WORKERS~5-10> <SPAN_TIMEOUT~3600>`
   — перезапускает индексер на каждый span. Идемпотентно (PK=chunk+block_number), безопасно
   зацепить уже-целые блоки по краям диапазона.
4. **⚠️ Не гнать backfill с заметным `FETCH_WORKERS` ОДНОВРЕМЕННО с живой индексацией на ТОЙ ЖЕ
   RPC-ноде** — может задушить и то, и другое (см. инцидент 2026-06-23, диск `.63` на 100%).
   Держать `FETCH_WORKERS=5-10` для backfill, проверять живую скорость не упала.
5. Финальная верификация — снова `find_missing_blocks.py` на том же диапазоне, должно быть 0.

### Восстановить/форсировать resume-точку вручную (когда автоматика не справилась)
`dynamic_tuner.py`'s `resume_from()` **приоритезирует последнюю `[watermark] N` строку В ЛОГЕ**
над любым явным `--from`/CLI-аргументом, который ты передашь тюнеру при запуске! Просто передать
новый `from_block` тюнеру НЕ сработает, если лог уже содержит более раннюю watermark-строку.
Чтобы форсировать новую resume-точку (например, после ручной записи "битого" блока в
`pol.skipped_blocks`):
```bash
ssh ... "echo '[watermark] <NEW_POINT>  # manual: причина' >> /data/pol_index/full_index_run/run_NN_v3.log"
```
Затем перезапустить как обычно — `resume_from()` подхватит новую строку. **Перед этим всегда**
прогнать `find_missing_blocks.py` на диапазон до `NEW_POINT`, чтобы убедиться, что пропуск только
ожидаемый (тот, что записываешь в `skipped_blocks`), а не что-то ещё.

### Записать явный пропуск вручную в БД
```bash
ssh ... "docker exec scylla cqlsh -u cassandra -p cassandra -e \"INSERT INTO pol.skipped_blocks (block_number, chunk, skipped_at, reason, resolved) VALUES (<N>, <CHUNK>, toTimestamp(now()), '<reason>', false);\""
```
`CHUNK = (N % 64) + 64 * (N // 32000)`.

### Известные грабли
- `nohup cmd1 & ; nohup cmd2 &` в ОДНОЙ ssh-команде — второй часто не стартует. Раздельные вызовы.
- `resume_from()` приоритет `[watermark]`-строки лога над CLI `--from` — см. выше.
- `Task.joinTimeout` (45с) на каждый HTTP под-запрос (block/receipts/traces) — если ВСЕ ТРИ висят,
  один блок может занять до ~135с до отказа от primary, прежде чем попробовать neighbor.
- give-up-счётчик теперь персистентный (задача #7 решена, см. ниже) — каждый воркер держит
  собственное Redis-подключение (`Conn.incr`/`Conn.del` в `src/db/cursor.zig`) и инкрементит
  `giveup:{blockNum}` в БД своего узла (db=0/.62, db=1/.63) вместо локальной переменной
  `cycleCount`; счётчик переживает рестарт процесса. При успехе/skip ключ удаляется (`del`), чтобы
  повторная обработка того же блока (например, backfill) не унаследовала старое значение. При сбое
  Redis (insert/connect ошибка) — fail-soft на `1` (не форсирует ложный give-up).
- HTTPS (паблик/backup RPC) — задача #4 решена 2026-06-23: вместо `std.http.Client` (TLS-стек
  которого крашит ReleaseFast, ML-KEM баг в Zig stdlib) для `https://`-урлов теперь используется
  `curl`-subprocess (`fetchViaCurl` в `src/core/common/fetch.zig`), полностью прозрачно для
  вызывающего кода (`client.zig`, `node_probe.zig` не менялись по сути). `RESERVE_RPC_URL`
  (которую `dynamic_tuner.py` и так выставляет) теперь реально подключена в `main.zig` как
  backup-нода. Подтверждено `zig test` напрямую на реальном паблик RPC
  (`polygon-bor-rpc.publicnode.com`) под `-OReleaseFast` — без SIGILL. Локальный патч Zig-тулчейна
  (удаление `x25519_ml_kem768`) оставлен как есть (безвреден, уже не критичен для прода).
- Сборка **только** `-Doptimize=ReleaseFast` (Debug вешает pool workers — баг Zig 0.17-dev).

Запуск (на сервере, раздельными ssh-вызовами из-за nohup-бага):
```bash
cd /data/pol_index/full_index_run
nohup python3 dynamic_tuner.py 62 http://100.64.0.62:8545 <FROM> 31124773 >> tuner_62.log 2>&1 &
nohup python3 dynamic_tuner.py 63 http://100.64.0.63:8545 <FROM> 89000000 >> tuner_63.log 2>&1 &
```
`<FROM>` — для резюме после рестарта: `grep -oP 'Accum \d+→\K\d+' tuner_NN.log` (сам tuner это
делает автоматически через `resume_from()`, читая `run_NN_v3.log`).

**Что делает tuner** (`tools/dynamic_tuner.py`):
- Пробует `FETCH_WORKERS` ∈ {100,200,300,400} по 90с каждый, измеряет blk/s и connection errors
  (`[ALERT] N connection errors` из лога), выбирает лучший без чрезмерных ошибок
- На "steady" период (30 мин) — следит за: (а) connection errors (если +10 за 30с — снижает
  FETCH_WORKERS ×0.6), (б) частотой рестартов процесса (если 3+ рестарта за 5 минут — тоже снижает
  ×0.6, это ловит Scylla-side ошибки типа "Batch too large", не только RPC-проблемы)
- После 30 минут steady — переребирает в окрестности текущего значения
- Шлёт все решения в GrayLog (`indexer-pol-NN-tuner` app)
- **Известное упущение**: пока НЕ повышает FETCH_WORKERS снизу вверх автоматически после
  длительной стабильности — только держит текущий, либо снижает. Если нужно увеличение нагрузки
  обратно после backoff — придётся подождать следующего штатного re-probe цикла (30 мин) или
  перезапустить вручную.

   сплошную границу сохранённых блоков независимо от порядка завершения, печатает `[watermark] N`
   (используется `dynamic_tuner.py` для resume вместо `Accum`-строки). С этого фикса `.62` не

## Задача #7 — решена

Реализовано как и планировалось: добавлены `Conn.incr(key) !i64` и `Conn.del(key)` (RESP
`INCR`/`DEL`) в `src/db/cursor.zig`. `WorkerArgs` получил поле `redisUrl: cursor.ParsedUrl`
(прокидывается из `runHistorical` → `spawnHistoricalWorkers`, который уже парсил `rUrl` для
основного чекпоинт-подключения). Каждый воркер в `worker()` открывает **своё** Redis-подключение
(`cursor.Conn` не thread-safe для шаринга между потоками) с тем же `auth`/`selectDb`, что и
основной чекпоинт — т.е. ключи `giveup:{blockNum}` естественно изолированы per-node через
`db=0`/`db=1`, как и watermark.

Новые хелперы в `pipeline.zig`:
- `bumpGiveupCycle(rdb, blockNum) -> u32` — `INCR giveup:{blockNum}`, на ошибке Redis fail-soft
  возвращает `1` (никогда не форсирует ложный give-up из-за сбоя Redis).
- `clearGiveupCycle(rdb, blockNum)` — `DEL giveup:{blockNum}`, вызывается при реальном успехе,
  при успехе на neighbor/backup и сразу после фактического give-up (чтобы повторная обработка
  того же блока, например при backfill, не унаследовала старый счётчик).

Все три точки `cycleCount += 1` в `worker()` заменены на `cycleCount = bumpGiveupCycle(rdb, blockNum)`.
Собрано и проверено `-Doptimize=ReleaseFast` — компилируется чисто. Блок `37343867`-сценарий (частые
рестарты процесса тюнером сбрасывали локальный счётчик до достижения `MAX_GIVE_UP_CYCLES`) теперь
не должен повторяться — счётчик переживает рестарт процесса. **Ещё не задеплоено на `100.64.0.64`**
(собран только локально) — нужен `scp` + restart (см. ШПАРГАЛКУ выше, не забыть `pkill` перед `scp`,
"Text file busy").

## 🔴 Открытый инцидент (внешний, не наш код): зависшая live-синхронизация Erigon на `.63`

Обнаружено 2026-06-23/24 в ходе расследования "почему деградировала скорость": это НЕ проблема
нашего индексера, это инцидент на самой RPC-ноде `.63` (`100.64.0.63`, контейнер `POL_ERIGON`,
erigon v3.6.0), требующий действий DevOps (владелец — maxim). Полная хронология и доказательная
база (для следующей сессии, если потребуется продолжить эскалацию):

**Что произошло**: 22 июня ~19:20 на `.63` стартовала фоновая агрегация state-trie
(`[4/6 Execution][agg] computing trie`, видно в `docker logs POL_ERIGON`) — заняла ~4.5ч, память
процесса (`sys`) выросла 54.5GB→76.1GB и **не вернулась обратно** (Go runtime не отдаёт RSS ОС).
Собственная live-синхронизация Erigon (стадия `[4/6 Execution]`, голова цепи — НЕ наш диапазон
31-89M, у Erigon отдельный счётчик) упала с штатных ~6.2 блк/с до ~0.6-1.0 блк/с и далее держалась
деградированной. Рестарт контейнера 23 июня 10:02:38 дал ~4.7ч жизни на той же деградированной
скорости, затем в **14:45 23 июня встала окончательно** — с тех пор (на момент последней
проверки) **0 блоков**, разрыв с реальной головой цепи растёт.

**Диагноз (через `http://100.64.0.63:6060/debug/metrics/prometheus`, `grep '^sync{'`)**: ВСЕ
стадии (`headers`/`bodies`/`execution`/`senders`/`finish`/`tx_lookup`) стоят на ОДНОМ числе — то
есть встал не execution (обработка), а сам headers/bodies download. При этом пиры подключены
(`net_peerCount`≈18-20, `[p2p] GoodPeers` стабильно), `bor.heimdall`-скрапер (консенсус-слой,
ОТДЕЛЬНАЯ удалённая Tendermint-цепочка с собственной нумерацией блоков — не путать с EVM-высотой)
активно прогрессирует. Найдена конкретная повторяющаяся ошибка:
```
[WARN] [sync] failed to backward download blocks ... source=p2p-new-block-hashes-source
  err="no peers available before reaching connection point num=X, hash=0x...: all peers exhausted"
```
— реактивный механизм докачки по P2P-анонсам новых блоков не может закрыть образовавшийся разрыв
(~21K+ блоков на момент находки), хотя пиры в принципе на связи. Сравнение с `.62` (`instance=
erigon`, без SSH-доступа, только метрики): там `headers`/`bodies` ОПЕРЕЖАЮТ `execution` (здоровый
конвейер, просто нагоняет разрыв ~65K блоков, который сокращается) — то есть на `.62` P2P-докачка
реально работает, на `.63` — нет, хотя у `.63` разрыв был МЕНЬШЕ. Проверено и исключено:
- НЕ из-за нашей нагрузки — полностью останавливали индексер на ~40с, высота не сдвинулась.
- НЕ "не набрал пиров" — пиры есть (18-20, стабильно).
- НЕ известный баг erigon issue #7498 (`pos sync failed`, remoteConsensusEngine) — ни одного
  совпадения в логах; к тому же у нас `--bor.heimdall=https://heimdall-api.polygon.technology`
  (удалённый, не локальный Heimdall), сам баг про локальный Heimdall не применим архитектурно.
- НЕ heimdall lag — удалённый Heimdall API подтверждён живым и свежим (`latest_block_time`
  совпадает с реальным временем до секунд).
- Restart НЕ помогает надолго (см. хронологию выше) — но 3 ПРЕДЫДУЩИХ рестарта (06-19 09:18,
  06-20 23:51 кластер из 6, 06-22 13:22) восстанавливались штатно за минуты. Аномален именно
  последний — видимо унаследовал повреждённое/незавершённое состояние с агрегации 19:20 22 июня.

**Официальная документация Erigon** (docs.erigon.tech/help-center) подтверждает механизм:
тяжёлая конкурентная RPC-нагрузка может "spam"-ить ноду и мешать sync-стадиям, и при упоре диска в
IOPS память начинает раздуваться буферизацией — частично совпадает с нашей находкой (наша нагрузка
в момент инцидента 19:20 была от СТАРОГО, ещё не пофикшенного тюнера, гнавшего FETCH_WORKERS до
300-400). Рекомендация документации при зависании — простой `docker restart`/`systemctl restart`,
конкретных команд для stage-level reset (`erigon integration` unwind) НЕ описывает.

**Срочное сообщение отправлено DevOps** (2026-06-23/24) с планом: (1) снять нашу нагрузку перед
рестартом — умеем сами; (2) `docker restart POL_ERIGON`; (3) мониторить именно
`sync{stage="headers"}` (не только `eth_blockNumber`) первые минуты — если headers не пойдёт
вперёд bodies/execution (как сейчас на `.62`), значит рестарт снова не помог; (4) если повторится —
нужен stage-level reset или полный ресинк из снэпшотов, простого рестарта недостаточно.

**Решение по нашей работе (2026-06-24)**: эта проблема **отложена в сторону** — на нашу
историческую индексацию (диапазон 31-89M, уже синхронизированный Erigon-ом ранее) зависшая
live-sync не влияет; мы читаем старые блоки, не голову цепи. Более того, отсутствие конкурентной
live-sync-нагрузки от самого Erigon, возможно, даже снизило давление на диск/память для наших
архивных запросов. Фокус сессии переключён на ускорение собственно индексации (см. фикс
`disk_busy` в тюнере выше).
