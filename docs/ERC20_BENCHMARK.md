# ERC20_BENCHMARK.md — историческая скорость индексации с ERC-20 трекингом

## Условия теста

- Тест-сервер `100.64.0.4` (та же машина, что обслуживает живой реалтайм-индексер `raw_dev_test_9`)
- ETH архивная нода: `http://100.64.0.7:8545` (RETH)
- ScyllaDB 6.2 в Docker: `--developer-mode 1 --unsafe-bypass-fsync 1 --overprovisioned 1` (тестовые флаги, в проде будут убраны — **итоговые цифры это нижняя граница**, на fsync-проде будет медленнее)
- Индексер: `workerCount=64`, default lanes `split=1,3,6,20,1,1`, `SAVE_EVERY=24` — конфиг подтверждён идентичным живому прод-процессу через `/proc/<pid>/environ`
- Redis изолирован в отдельные logical DB (2/3/4/5/6) на каждый прогон, чтобы не трогать курсор `LATEST_PROCESSED_BLOCK_NUMBER` живого реалтайм-процесса в DB 0
- Время — "чистое", из таймера `Historical sync done: Xms`, который в коде стартует **после** открытия Scylla/Redis-соединений и спавна воркеров (исключает разовый connection-setup оверхед)
- Голова цепи на момент теста: блок 25,339,645

## Этап 1 — грубая выборка (25 окон × 1000 блоков, по одному на каждый миллион)

Окна центрированы в середине каждого миллиона (0.5M, 1.5M, ..., 24.5M).

| Блоки (млн) | blk/s (до батчинга) | Новых ERC-20 кандидатов в окне |
|---|---|---|
| 0–6 | 980–1443 | 0 (до EIP-20 эры) |
| 7–12 | 92–218 | 318–1704 |
| 13 | 77.8 | **4129** (burst-деплой, антипик) |
| 14–24 | 50–113 | 42–402 |

**Найденный и исправленный баг:** офсеты элементов динамического массива в ABI-кодировке `aggregate3` писались относительно начала tail-секции, а не относительно начала всего массива (без учёта размера head-секции) — каждый вызов к Multicall3 делал revert. Исправлено в `src/rpc/multicall.zig`, проверено через прямой `eth_call` + сверку с эталонным `eth_abi` (Python).

**Объём данных (экстраполяция по 25 точкам):** ≈ 9987 кандидатов на 25 000 просэмплированных блоков → **≈ 10.07M ERC-20-кандидатов** на всю историю (это кандидаты по bytecode-selector эвристике, включая спам/клоны фабрик — не "подтверждённые" токены). Замер на диске (`du` по SSTable, LZ4-сжатие): **168.6 байт/токен** (tokens+supplies+owners) → **≈ 1.7 GB** суммарно на `eth.erc20_*`.

## Этап 2 — оптимизация: батчинг кандидатов по всему accum-окну

Раньше `resolveAndEnrich` резолвил ERC-20 метаданные через Multicall3 **по одному блоку за раз** — отдельный RPC round-trip на каждый блок с кандидатами внутри окна аккумуляции. Это било по плотным/burst-окнам (см. million=13 выше).

`resolveAndEnrichWindow` (коммит `6fa2f4c`) собирает кандидатов/touches/self-destructs **со всех блоков окна** перед резолвом — N round-trip'ов на блок сжимаются в ~1 (с тем же chunking по `multicallChunkSize`). Все адреса окна резолвятся "as of" последнего блока окна, а не точного блока создания каждого кандидата — в пределах ~24 блоков (~5 мин на ETH) состояние свежесозданного токена практически не меняется.

Повторный прогон тех же 25 окон после оптимизации:

| Million | до | после | Δ% |
|---|---|---|---|
| 6–8 (умеренная плотность) | 203–254 | 283–320 | **+26…+41%** |
| 13 (burst) | 77.8 | 89.2 | +14.5% |
| 17, 20 | 80.8 / 84.3 | 110.9 / 95.9 | +37.3% / +13.8% |
| 10–12, 18–19, 21–24 (самые плотные по обычным tx/log) | — | — | **−2…−8%** (эффект тонет в шуме общей загрузки блока) |

Итог по всем 25 окнам: суммарное время 208.1с → 200.4с (**−3.7%**). Эффект максимален там, где ERC-20-резолюция была заметной долей общего времени блока (умеренная плотность), и тонет в шуме на самых "тяжёлых" по обычным данным диапазонах.

## Итоговая оценка полной исторической синхронизации (genesis → head)

| Метод | Оценка |
|---|---|
| Грубая (25×1000 блоков, по 1 точке/млн) | ≈ 57 часов (2.4 суток) |
| **Плотная (253×100 блоков, шаг 100k)** | **≈ 71.6 часов (2.98 суток)** |
| Эффективная средняя скорость | ~98.3 blk/s |

Плотная оценка выше грубой — статистический эффект: редкая выборка случайно попадала на не самые медленные участки внутри каждого миллиона.

**Важные оговорки:**
1. Цифры — на тестовом Scylla без fsync (`--unsafe-bypass-fsync`). На реальном проде (с fsync) будет медленнее, величина не измерена.
2. `ERC20CONTEXT.md` указывает базовую скорость прод-индексера (без ERC-20) **13–20 blk/s** для плотной эры (10–25M) — это в 5–10x медленнее измеренного здесь (50–150 blk/s). Вероятная причина: тот замер был под полной production-нагрузкой (параллельные потоки, реальный диск/сеть), здесь сервер существенно легче нагружен. Если ориентироваться на документированный baseline 13–20 blk/s, полная индексация может занять не 3 суток, а **2–3 недели**.
3. ERC-20-функциональность (с батчингом) добавляет сравнительно небольшой оверхед к базовой скорости индексера — десятки процентов в худшем случае, не кратное замедление.
4. Конфигурация Scylla (`developer-mode`/`fsync`/`overprovisioned`) не менялась намеренно — трогать боевые флаги на сервере с живым реалтайм-процессом без отдельного обсуждения признано слишком рискованным.
