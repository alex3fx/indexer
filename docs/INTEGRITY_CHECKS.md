# Проверка целостности данных — методология и журнал верификаций

_Создано: 2026-06-23._ Принцип проекта: целостность данных — приоритет №1, никаких допустимых
потерь строк, даже на уровне 0.001% (см. `CLAUDE.md`). Этот документ описывает, как мы проверяем
полноту данных в Scylla и где хранится журнал прошлых проверок.

## Журнал верификаций — таблица `pol.integrity_checks`

Результаты всех проверок целостности записываются в саму базу:

```sql
CREATE TABLE pol.integrity_checks (
    check_id timeuuid,
    checked_at timestamp,
    node text,                 -- '62' / '63' / etc — какой индексер-процесс покрывает диапазон
    range_from bigint,
    range_to bigint,
    missing_count int,
    missing_blocks list<bigint>,  -- сами номера, если missing_count небольшой
    tool text,
    notes text,
    PRIMARY KEY (node, check_id)
) WITH CLUSTERING ORDER BY (check_id DESC);
```

Посмотреть последние проверки:
```sql
SELECT node, checked_at, range_from, range_to, missing_count, tool, notes
FROM pol.integrity_checks;
```
(доступно read-only пользователю `reader`, см. `docs/SCYLLA_READONLY_ACCESS.md`)

## Явные пропуски — таблица `pol.skipped_blocks`

С 2026-06-23 `worker()` (`src/pipeline/pipeline.zig`) после исчерпания primary → neighbor →
backup (5 полных циклов с backoff) **не виснет навсегда** — он явно записывает блок в эту таблицу
и продолжает работу (watermark корректно продвигается дальше):

```sql
CREATE TABLE pol.skipped_blocks (
    block_number bigint PRIMARY KEY,
    chunk int,
    skipped_at timestamp,
    reason text,
    resolved boolean
);
```

Такой блок **не получает строку** в `blocks` (и остальных таблицах) — `find_missing_blocks.py`
корректно продолжит видеть его как пропуск до отдельного ручного backfill. Посмотреть текущий
список нерешённых:
```sql
SELECT * FROM pol.skipped_blocks WHERE resolved = false;
```
(`ALLOW FILTERING` может понадобиться в зависимости от версии Scylla — таблица маленькая, не
проблема для редких записей)

После ручного backfill конкретного блока (например, через паблик RPC или повторную точечную
попытку) — обновить `resolved=true`:
```sql
UPDATE pol.skipped_blocks SET resolved = true WHERE block_number = <N>;
```

## Как проверяем — `tools/find_missing_blocks.py`

Для v3 chunk-схемы (`chunk = (block % 64) + 64 * (block / 32000)`) каждый `lane` (`block % 64`)
внутри одной `era` (`block / 32000`) — это арифметическая последовательность с шагом 64 в своей
партиции. Скрипт сканирует **все 64 lanes** по каждой `era` в заданном диапазоне `[from, to)`,
сравнивает present vs expected номера блоков и выводит точный (не оценочный) список пропущенных.

```bash
python3 tools/find_missing_blocks.py FROM_BLOCK TO_BLOCK [LANES=64] [ERA=32000] [TABLE=blocks] [CONCURRENCY=64]
```

Почему не просто `SELECT count(*)` по диапазону: подсчёт строк не отличит "пропущенный блок" от
"блок с естественно нулевым количеством строк" в таблицах типа `logs`/`internal_transactions`/
`contracts` (где у пустых блоков просто не будет строк). Сравнение по таблице `blocks` (где у
КАЖДОГО блока всегда ровно 1 строка) — самый надёжный сигнал "этот блок вообще обработан".

## Известные инциденты и их разбор

### 2026-06-23: зависший воркер, watermark отстал от живого прогресса на ~780K блоков

Несколько воркеров `.63` поймали `ConnectionRefused` при старте процесса, начали ретраить через
"never giving up" логику (`pipeline.zig`), но один из них **завис навсегда** внутри HTTP-вызова
(нет таймаута на чтение в `std.http.Client` — см. `src/core/common/fetch.zig`) — больше 1.5 часа
без единой новой строки лога. Другие воркеры продолжили обработку и ушли на ~780K блоков вперёд;
watermark (резюм-точка) корректно НЕ продвигался, ожидая зависший блок.

**Проверка показала: пропущен ровно 1 блок** (`37343867`, сам зависший) из 6.8М проверенных — все
его 14 "соседей" по тому же сбойному батчу успешно сохранились. Это подтверждает, что
watermark-механизм работает корректно (никакой тихой потери), цена инцидента — только повторная
обработка диапазона при рестарте (идемпотентная перезапись, не потеря).

**Фикс**: добавлен `Task.joinTimeout()` (45с) в `src/rpc/client.zig` — если HTTP-запрос не
завершается за 45 секунд, поток с зависшим запросом отбрасывается (утечка треда/памяти, без
data race — см. комментарии в коде), используемый `FetchClient` пересоздаётся, и retry-цикл
воркера продолжает работу вместо вечного зависания.
