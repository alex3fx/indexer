# FULLCHAIN_PREP.md — подготовка к полной индексации (genesis → head)

## 1. Worker count: сколько воркеров оптимально для нашей ноды

Гипотеза была: на полигон-ноде (48 ядер, **erigon**) 200 воркеров дают максимум throughput — нужно
проверить тот же диапазон для нашей ETH-архивной ноды (`100.64.0.7:8545`, **RETH**, не erigon).

Тест: `~/lotos/task1/fetcher` (отдельный Go-бенчмарк, чистый fetch — `eth_getBlockByNumber` +
`eth_getBlockReceipts` + `trace_block`, без парсинга/записи) — те же 3 RPC-вызова на блок, что и у
индексера (`src/rpc/client.zig`). Прогон **обязательно с тест-сервера** `100.64.0.4` (48 ядер) — с
домашней машины RTT до ноды 100-400мс (VPN), что полностью искажает результат; с тест-сервера RTT
<1мс (та же сеть). Окно: 2.45M последовательных блоков в зоне 24.5M, по ≤60с на каждый воркер-каунт.

| workers | blk/s | avg fetch ms | max fetch ms |
|---|---|---|---|
| 16 | 34.8 | 457 | 2398 |
| 32 | 52.4 | 606 | 2480 |
| 48 | 57.9 | 822 | 2758 |
| **64** | **62.2** | 1018 | 3119 |
| 96 | 57.7 | 1640 | 3256 |
| 128 | 54.0 | 2322 | 4374 |
| 160 | 52.2 | 2995 | 5034 |
| 200 | 54.2 | 3576 | 6478 |
| 256 | 52.4 | 4690 | 7272 |
| 320 | 29.9 | 9497 | 48159 |
| 400 | 26.5 | 12600 | 59398 |

**Вывод:** пик — **64 воркера** (62.2 blk/s) — это уже текущий `workerCount=64`
(`src/core/constants/chains/evm/ethereum.zig:20`). От 96 до 256 — плато 52-58 blk/s (немного хуже
пика, не катастрофично). После ~300 — деградация: латентность на блок взлетает с ~1с до 9-13с
(avg), max — до 48-59с, классический признак переполнения очереди на стороне ноды.

200 воркеров, которые помогают на erigon-ноде, **не помогают на RETH** — она хуже параллелит
`trace_block` (вероятно, ограниченный/последовательный пул экзекьюторов для трассировки старых
блоков). Текущий конфиг `workerCount=64` менять не нужно — он уже на оптимуме для этой ноды.

## 2. Оценка времени полной синхронизации

Уже задокументировано в `ERC20_BENCHMARK.md` (плотная выборка 253×100 блоков, шаг 100k, по всей
цепи 50K→25.25M):

- **≈ 71.6 часов (2.98 суток)** на тестовом Scylla без fsync (`--unsafe-bypass-fsync`).
- Прод с fsync будет медленнее, величина не измерена напрямую. Если ориентироваться на
  документированный прод-бейзлайн без ERC-20 (13-20 blk/s для плотной эры 10-25M) — возможна
  **2-3 недели**.
- ERC-20-функциональность с батчингом (`resolveAndEnrichWindow`) добавляет десятки процентов
  оверхеда, не кратное замедление.

Из текущего свипа (п.1) видно, что throughput воркеров **не является узким местом** в этом
диапазоне (62 blk/s чистого fetch против ~40-50 blk/s полного пайплайна на индексере в той же зоне
24-25M) — bottleneck в основном на стороне `trace_block` ноды и на стороне записи/трансформации,
не на конкурентности клиента.

## 3. Диск / объём данных

**Первая оценка (73 MB / 349K блоков → единицы ГБ на всю цепь) была неверной — отброшена.**
Причины: (а) `erc20_*` и `block_completions` не попали в `du` — у них нет SSTable-директорий на
диске, данные ещё в memtable/commitlog (`nodetool flush` не работает: на сервере не хватает
`fs.aio-max-nr`, 1,059,571 vs нужных ~1,070,579 — трогать sysctl на этом хосте решили не делать);
(б) `COUNT(*)` по `transactions`/`logs`/`internal_transactions` (1.3M+ строк) упирается в таймаут
read-запроса; (в) накопленный тестовый набор — смесь перекрывающихся прогонов, не репрезентативная
выборка по плотности.

**Пересчёт через RPC ground truth.** `~/lotos/task1/fetcher -parse` (чистый fetch + подсчёт
строк из реального RPC-ответа, без зависимости от того, что уже лежит в Scylla) по 7 точкам
1M→25.3M:

| 1M | 5 | 0 | 6 |
| 5M | 172 | 92 | 245 |
| 10M | 144 | 146 | 352 |
| 14M | 197 | 297 | 704 |

Экстраполяция по зонам (границы зон — как в `ERC20_BENCHMARK.md`, плотность зоны = плотность

Это **flat-rate по зоне** экстраполяция (плотность внутри зоны не растёт плавно, а берётся по

(схема `minified/*` — урезанные поля, не полный RLP, но судя по уже измеренному erc20-кейсу —
168.6 байт/токен на компактную схему из ~12 колонок — сжатие у узких Cassandra/Scylla-строк хуже
ожидаемого из-за per-cell overhead) — итоговый объём **порядка сотен ГБ — низких единиц ТБ**, не
единиц ГБ, как было сказано раньше.

- На сервере свободно **1.2 TB** из 2 TB.

**Это меняет вывод раздела полностью: на сервере свободно 1.2 TB — этого хватит в лучшем случае на
~2% полной цепи. Диск — не риск, а жёсткий блокер для запуска полной индексации на этом железе.**
Нужно либо (а) на порядок больше дискового пространства, либо (б) сократить набор хранимых полей
(особенно `contracts_by_addresses` — 16.5 КБ/строку, явно избыточно для lookup-таблицы — и
`internal_transactions`, которая физически больше всех по числу строк), либо (в) ограничить глубину
истории (хранить не genesis→head, а последние N блоков/лет).

**Заодно объясняет и замер скорости — и это методологическая ошибка прошлых бенчмарков, не
особенность прода.** Контрольный прогон на 1М блоков в зоне 24.3M шёл не на ожидаемых 40-55 blk/s,
а на ~3.2 blk/s устойчиво — `iostat` показал `md2` (RAID-массив под Scylla) на 100% utilization
(~250 МБ/с записи), а `/compaction_manager/compactions` — несколько активных компакций на
`transactions`/`internal_transactions` в реальном времени. Причина разницы:

- Старые бенчмарки (`bench_hist_zones.sh`, `erc20_bench_dense*.sh`) запускали **отдельный
  процесс** `--from=X --to=Y` на 100-2000 блоков, который завершается сразу после
  `Historical sync done: Xms` (`main.zig`: `if (cli.to != null) return;`).
- CQL `INSERT` подтверждается, когда запись попала в memtable/commitlog — **не после компакции**.
  Сама компакция (flush memtable → merge SSTable) у Scylla асинхронная, фоновая, и продолжается
  уже после того как клиент отключился и процесс вышел.
- Значит таймер `Historical sync done` мерил только время "дойти до memtable" (чистый
  network+CQL round-trip) — короткое окно процесса просто не успевало упереться в реальную
  пропускную способность диска. `bench_hist_zones.sh` к тому же делал `TRUNCATE` между прогонами —
  каждый замер стартовал с пустых таблиц, без существующих SSTable для слияния.
- При длинном sustained-прогоне (1М блоков в одном процессе) Scylla рано или поздно перестаёт
  успевать flush+compaction за темпом записи и начинает тормозить новые `INSERT` (backpressure) —
  именно это и проявилось как просадка до ~3.2 blk/s.
- fsync — вторичный фактор: **первая** попытка контрольного прогона (до рестарта Scylla, ещё под
  `--unsafe-bypass-fsync 1`) тоже шла на ~5 blk/s, не 40-55 — то есть даже без честного fsync
  длинный прогон упирался в ту же стену компакции. Главная причина разницы — длительность
  прогона (short burst vs sustained), не флаг fsync.

**Практический вывод (на момент обнаружения):** все цифры throughput в `ERC20_BENCHMARK.md`
(40-983 blk/s) — это "burst"-скорость до memtable, не sustained-скорость с учётом компакции.
Оценки времени полной синхронизации (2.98 суток / 2-3 недели), посчитанные на этих цифрах,
выглядели завышенными: sustained-скорость в плотной зоне (~3.2 blk/s) давала ≈92 дня (≈3 месяца)
на всю цепь. **Это было устранено переносом хранилища — см. ниже.**

## 3.1 UPDATE (2026-06-20): корень проблемы найден и устранён — перенос на /storage

И блокер по месту (13.5 TB нужно / 1.2 TB свободно), и просадка sustained-скорости (3.2 blk/s)
оказались **одной и той же инфраструктурной проблемой**, не особенностью прода и не байтами в коде.

**Где была проблема:** Scylla писала в `/var/lib/docker/volumes/.../_data` → `/` (root, `md2`) —
RAID1-зеркало из 2× Intel D7-P5510 3.84TB, общее с ОС. Дополнительно `iostat` показал
`/etc/scylla.d/io.conf` с `--max-io-requests=1 --num-io-queues=1` — Scylla был сконфигурирован
буквально на **один** I/O запрос за раз, независимо от реальной скорости диска. Честная
калибровка (`iotune`, после поднятия `fs.aio-max-nr` с 1,059,571 до 1,600,000 — по запросу самого
iotune, разовая безопасная правка, ничего не перезапускает) показала реальные параметры диска:
**4316 MB/s sequential write, 6899 MB/s sequential read, 34,923 write IOPS, 41,976 read IOPS** —
то есть диск в 10-17x быстрее, чем то, что мы видели (250-400 MB/s).

**Решение:** перенос данных (`rsync`, без потерь — проверено сверкой `SUM(tx_count/log_count/
itx_count/contract_count)` по `block_completions` до/после) на `/storage` — выделенный LVM-том
20.96 TiB на 3× энтерпрайз NVMe (2× Samsung MZQL27T6HBLA 7TB + 1× Kioxia KCD81RUG7T68 7TB),
не разделяемый с ОС. (Калибровку `io_properties.yaml` Scylla не подхватила — `--overprovisioned`,
который docker-entrypoint принудительно восстанавливает из-за нехватки capabilities хоста для
честного bare-metal режима, видимо игнорирует файл калибровки. Не блокирует: сам перенос на
выделенный диск дал основной эффект эмпирически, без формально применённой калибровки.)

**Результат — sustained-скорость на новом диске для зоны 24.4-24.6M:**

| Тест | Условия | blk/s |
|---|---|---|
| "100 через 100k" (старый burst-тест) | 24,550,000-24,550,099, 100 блоков | 38.87 |
| "1000 на 1M" (старый burst-тест) | 24,500,000-24,500,999, 1000 блоков | 50.29 |
| **Sustained на новом диске** | 24,445,918-24,622,003, ~176K блоков, **целый час** | **≈49** |

**Деградации между burst и sustained больше нет** — устойчивая скорость практически совпадает со
старыми "обманчивыми" короткими тестами для этого же диапазона (49 против 38.87-50.29). Новый
диск достаточно быстрый, чтобы компакция не создавала backpressure на этом темпе записи —
методологическая проблема (короткие тесты не видели стоимость компакции) перестала иметь значение,
потому что реальная sustained-скорость теперь не хуже burst-скорости.

**Пересчёт оценки полной синхронизации:** на sustained ~49 blk/s для плотной зоны 25.36M блоков ⇒
≈ **6 дней** (вместо ≈92 дней на старом диске). Это по одной зоне (24.4-24.6M, около часа
наблюдения) — для уверенности стоит повторить sustained-замер ещё в 1-2 других плотных зонах
(особенно у головы цепи, ~25.3M, где плотность логов/itx выше всего — `2060 itx/блок` против
`850` на 22M), но качественный вывод уже ясен: **проблема со скоростью решена переносом диска**, не
требует дальнейшей оптимизации кода индексера.

**Объём диска:** на `/storage` свободно ~20 TB против оценки **13.5 TB на всю цепь** (раздел 3) —
запас ~6.5 TB, уже не "жёсткий блокер", а комфортный (хотя и не огромный) запас. `/storage` —
linear LVM (не striped, см. `SCYLLA_STORAGE_MIGRATION.md`), без redundancy на уровне ОС (раньше
было RAID1) — компромисс, который стоит держать в уме отдельно от скорости/места.

## 4. Устойчивость соединений / отказоустойчивость

Уже сделано и закоммичено (`45ce0dc`): auto-reconnect + health-check для Scylla/Redis (`ping()` /
`reopen()`, периодическая проверка каждые `DB_HEALTH_CHECK_INTERVAL_MS=60_000` в реалтайм-цикле),
socket-таймауты (`SO_RCVTIMEO`/`SO_SNDTIMEO`) на CQL/Redis/WSS/GrayLog. Проверено живым тестом —
убийство всех CQL-сокетов процесса не приводит к падению, восстановление автоматическое.

Для исторического (не реалтайм) режима отдельного health-check/reconnect цикла нет — но при сбое
соединения `saveEntitiesParallel` вернёт ошибку, `pipeline.zig` не глотает её молча
(`if (g.err) |e| return e` и т.п.), процесс завершится с ошибкой, а не продолжит с дырой в данных.
Рестарт после краша безопасен — см. п.6 (идемпотентность) и п.5 (курсор).

## 5. Чеклист перед запуском полной индексации

1. **Зафиксировать конфиг** — `workerCount=64` (не менять, см. п.1), `SAVE_EVERY=24`,
   `SCYLLA_CHUNK_BUCKETS=24` (текущие дефолты, `pipeline.zig:40,45`), `minifiedChunkSize=1000`.
2. **Scylla flags — обновлено.** `--unsafe-bypass-fsync` снят (см. п.3.1), реальный fsync уже
   работает. `--developer-mode`/`--overprovisioned` docker-entrypoint автоматически восстанавливает
   обратно — хосту не хватает capabilities (perf_event, полный AIO) для честного bare-metal
   режима; калибровка `io_properties.yaml` из-за этого не подхватывается формально, но перенос на
   `/storage` дал нужный эффект и без неё (sustained-скорость ≈ старым burst-цифрам, см. п.3.1).
   Дальше можно не трогать, если sustained-скорость в других зонах подтвердит то же самое.
3. **Backup RPC-нода** — `retryMissingBlocks` использует `backupNode`, если он не настроен — любой
   блок, не отданный primary, останавливает синхронизацию (`error.MissingHistoricalBlocks`).
   Стоит подтвердить, что backup сконфигурирован, иначе единичный сбой ноды на 25M блоках может
   потребовать ручного перезапуска ровно с того места.
4. **Курсор изолирован** — убедиться, что `CM_CONNECTION_URL` боевого запуска использует чистую/
   новую Redis-БД (`LATEST_PROCESSED_BLOCK_NUMBER`), не одну из тестовых logical DB (2-7), которые
   использовались в этой сессии для бенчмарков.
5. **GrayLog/мониторинг** — логгер уже шлёт `log.err`/`log.warn` в GrayLog с реконнектом на
   обрыв (`SO_SNDTIMEO=5s`); подтвердить, что дальше есть алертинг на эти сообщения (fatal-блоки,
   reconnect-события), а не только пассивный лог.
6. **План на случай долгого прогона (дни/недели)** — учитывая оценку 3 дня - 3 недели, заранее
   продумать: куда смотреть на прогресс (курсор в Redis = текущий синхронизированный блок), как
   быстро отличить "медленно, но идёт" от "застряло" (см. п.6 — мониторинг через
   `block_completions`).
7. **Следить за диском с первого дня** — даже после переноса на `/storage` (~20TB) запас над
   оценкой (~13.5TB) всего ~6.5TB, не безграничный; после первых ~500K-1M реально обработанных
   блоков пересчитать прогноз на остаток цепи по факту, не дожидаясь, пока диск кончится сам.
   Использовать правильный путь (`/storage/scylla-eth`, не старый `/var/lib/docker/volumes/...`,
   см. `SCYLLA_STORAGE_MIGRATION.md`).
8. **Sustained-скорость подтверждена только для одной зоны** (24.4-24.6M, ~49 blk/s за час) —
   перед полным запуском стоит повторить такой же sustained-замер (не burst!) хотя бы у головы
   цепи (~25.3M, самая плотная по логам/itx зона), чтобы исключить, что там диск всё-таки
   упирается в потолок на более высокой плотности записи.

## 6. Валидация данных и гарантии консистентности

### Гарантии консистентности (что система обеспечивает)

- **At-least-once, не exactly-once.** Запись блока — `INSERT` по первичному ключу (адрес/
  хэш/номер блока) → идемпотентно. Если процесс упал между записью данных блока и продвижением
  курсора, при перезапуске блок будет обработан повторно — это безопасно (перезапись тех же
  значений), не создаёт дублей/расхождений.
- **Курсор продвигается строго после всех записей.** `saveEntitiesParallel` → ошибка из любого из
  потоков (blocks/contracts/erc20/txs/logs/itxs) обрывает сохранение всего батча
  (`src/db/batch.zig`, после `errdefer`-джойна потоков — `if (g.err) |e| return e` для каждой
  лейны) → курсор (`LATEST_PROCESSED_BLOCK_NUMBER`) обновляется только после успешного
  `saveBlockCompletionsBatch`. Частичная запись блока без продвижения курсора возможна (отдельные
  таблицы не атомарны друг с другом — Scylla не поддерживает мультитабличные транзакции), но при
  перезапуске весь блок будет переписан целиком, что устраняет частичность.
- **Нет тихих пропусков в историческом режиме.** Если блок недоступен ни на primary, ни на backup
  RPC — `retryMissingBlocks` возвращает `error.MissingHistoricalBlocks`, синхронизация не переходит
  в реалтайм с дыркой в данных (`pipeline.zig:730-733`).
- **`block_completions`** — независимая таблица-аудит: на каждый сохранённый блок пишется
  ожидаемое количество строк (`tx_count`, `log_count`, `itx_count`, `contract_count`). Это даёт
  способ проверить полноту *после* факта, без необходимости держать всё в памяти во время прогона.

### Как валидировать итоговые данные

1. **Полнота диапазона (gap-check).** Для каждого `chunk` в `block_completions` номера блоков
   должны быть непрерывны на ожидаемом диапазоне. Запрос вида
   `SELECT block_number FROM block_completions WHERE chunk=? ORDER BY block_number` по каждому
   чанку (`chunk = block / minifiedChunkSize`, см. `pipeline.zig`) и сверка с ожидаемой
   последовательностью — находит пропущенные блоки быстрее полного пересчёта.
2. **Сверка количества строк.** Для выборки блоков — `tx_count`/`log_count`/`itx_count` из
   `block_completions` должны совпадать с `COUNT(*)` по `transactions`/`logs`/
   `internal_transactions` с тем же `block_number` (частичные записи или потерянные строки иначе
   не обнаружить).
3. **Сверка с RPC ground truth по контрактам (как уже делали для теста на 20M).** Скрипт вида
   `verify_erc20.py` — для случайной выборки адресов из `erc20_tokens`/`erc20_total_supplies`
   делать `eth_call` (`name`/`symbol`/`decimals`/`totalSupply`) к архивной ноде на `"latest"` и
   сравнивать с тем, что записано в Scylla. На 5000-блочном тесте около 20M это уже сделано:
   7 случайных токенов + 2 edge-кейса (null-значения) + проверка `owner` — все совпали.
4. **Сверка блоков/транзакций со сторонним источником.** Для случайных блоков — сравнить
   `block_hash`/`tx_count`/`gas_used` из таблицы `blocks` с ответом `eth_getBlockByNumber` от ноды
   (или, если есть доступ — со сторонним explorer API) — независимая проверка, что транзформация
   не искажает данные при парсинге.
5. **Сквозная проверка курсора.** В конце прогона `LATEST_PROCESSED_BLOCK_NUMBER` в Redis должен
   совпадать с фактической головой цепи на момент завершения (с учётом того, что голова двигалась
   во время многодневного прогона) — финальная проверка перехода в реалтайм-режим без зазора.

### Чего система НЕ гарантирует (явно)

- Нет мультитабличной атомарности — отдельные таблицы для одного блока пишутся параллельными
  потоками, и могут оказаться в промежуточном состоянии при крахе процесса *до* продвижения
  курсора (устраняется повторной обработкой при перезапуске — см. выше).
- Нет защиты от RPC-ноды, отдающей неконсистентные данные (e.g. trace при reorg) — резолюция
  ERC-20 "as of" последнего блока окна аккумуляции (см. `ERC20_BENCHMARK.md`, этап 2) — это
  осознанный компромисс точности на ~24 блока ради скорости, не баг.
