### [2026-07-24] Inner-phantom фикс в transformer.zig

**Запрос:** Проверить, внесён ли фикс inner-phantom (executed-but-reverted-by-parent) в Zig.

**Результат:** Фикс НЕ был внесён — реализован сейчас.

**Суть проблемы:** CREATE-субвызов имеет `result.address` (выполнился успешно на своём уровне), но родительский субвызов имеет `error=Reverted` в trace — EVM откатывает всё дерево. Outer-tx status=1. `eth_getCode=0x`. Наш трансформер записывал адрес в Scylla.

**Пример:** block 23,204,055, tx `0xa4dcf1482d...`, addr `0x53f9fc22...` — CREATE с code=1860 байт, но родитель `[1,2,8,3]` → Reverted.

**Изменения (3 файла):**

`src/rpc/types.zig` — добавлены поля `RpcTrace`:
```zig
traceErr: ?[]const u8 = null,   // "error" из Parity trace
traceAddress: []i32 = &.{},     // позиция в call-tree
```

`src/pipeline/parser.zig` — `parseTrace()` теперь парсит `"error"` → `traceErr` и `"traceAddress"` → `traceAddress` (добавлена `parseIntArray`); ранее оба поля игнорировались (`p.skip()`).

`src/pipeline/transformer.zig`:
- Pre-pass перед основным циклом — собирает `revertedAddrs[]` из трейсов с `traceErr != null`
- В CREATE-секции (после проверки `status==0`): `for (revertedAddrs) |rev| { if isPrefix(rev, trace.traceAddress) → break true }` — пропускает inner-phantom

**Сборка:** успешна (ReleaseFast, 0 ошибок).
**Статус:** не задеплоено. Нужен commit + scp + новый бинарь (следующий после v22).

### [2026-07-16] Какие именно ITX попадают/не попадают в базу для geth и reth

**Запрос:** внимательно посмотри, разница по эрам противоречива, мне нужно описание того, какие именно itx попадают и не попадают в базу для geth и reth

**Ответ:**

**reth `trace_block` (Parity format) — поля action по типу трейса:**

| reth type | callType | `from` в action | `value` в action | txHash | reth эмиттирует? |
|-----------|----------|----------------|-----------------|--------|-----------------|
| call | call | ✓ | ✓ | ✓ | ✓ |
| call | staticcall | ✓ | ✓ ("0x0") | ✓ | ✓ |
| call | delegatecall | ✓ | ✓ | ✓ | ✓ |
| call | callcode | ✓ | ✓ | ✓ | ✓ |
| create | — | ✓ | ✓ | ✓ | ✓ |
| suicide | — | **нет** (`address` field) | **нет** (`balance` field) | ✓ | ✓ |
| reward | — | **нет** (`author` field) | ✓ | **null** | ✓ |
| call to 0x01–0x0a | * | — | — | — | **нет** |

**Что попадает в нашу `internal_transactions`:**

| reth trace | в БД? | причина |
|------------|-------|---------|
| call (все subtypes) | **YES** | from≠"" AND value≠null AND есть txHash |
| create | **YES** | from≠"" AND value≠null AND есть txHash |
| suicide | **НЕТ** | `action.from=""` → fromAddr.len=0 → фильтр |
| reward | **НЕТ** | `transactionHash=null` → txIdxOpt=null → `continue` |
| call to precompile 0x01–0x0a | **НЕТ** | reth не эмиттирует |

**Dune (`ethereum.traces`, Erigon):**  
type='call' = все subtypes. dune_adj = call к non-precompile + create (suicide и precompile исключены явно).  
Reward: в `ethereum.traces` не присутствует.

**Вывод про противоречие знаков:**  
После всех корректировок (precompile: reth не эмиттирует, Dune вычитает; suicide: reth fromAddr="", Dune `type!='suicide'`; reward: оба не считают) оба множества **должны совпадать**. ### [2026-07-16] Root cause смены знака delta: адрес 0x100 (secp256r1 precompile, Pectra hardfork)

**Запрос:** (из предыдущего контекста) найти EOA staticcalls которые Erigon эмиттирует а reth — нет, посчитать за всё время. Идентифицировать конкретный механизм смены знака.

0x0000000000000000000000000000000000000348  →   20,098

**Ключевое открытие: адрес 0x100 объясняет 99.98% delta(24M).**

**Query 8002223** (0x100 по эрам 19M–25.5M):

**Блок 24706170 (delta_old = +19, hex 0x178fc7a):**
- reth trace_block → 968 трейсов
- 19 вызовов к 0x0000000000000000000000000000000000000001 (ecRecover) на traceAddress=[]
- Прямые EOA → precompile транзакции. BC = 968 (включает эти 19)
- dune_adj_old: Erigon трейсит те же 19 вызовов, потом формула их вычитает (-0x01–0x0a) → 949
- delta = 968 − 949 = **+19 точно** ✓

**Блок 24700094 (delta_old = −3, hex 0x178e4be):**
- reth trace_block → 3720 трейсов, 0 вызовов к precompile-адресам
- BC = 3720. dune_adj_old = 3723 (3 Erigon-only вызова к 0x100, reth не трейсит post-Pectra)
- delta = −3 **точно** ✓

**Root cause: ошибка формулы dune_adj_old**

```
BC = reth_all  (включает reth_0x01_0x0a)
dune_adj_old = erigon_all − suicide − erigon_0x01_0x0a   ← ошибка: удаляем 0x01–0x0a
delta_old = −erigon_0x100(post-Pectra) + reth_0x01_0x0a
corrected_delta = delta_old + erigon_0x100 + erigon_BLS = reth_0x01_0x0a

true_delta (правильная формула, без удаления 0x01–0x0a):
= BC − dune_adj_true = reth_0x01_0x0a − erigon_0x01_0x0a = 0
```

reth ДЕЙСТВИТЕЛЬНО трейсит прямые EOA-транзакции к 0x01–0x0a (traceAddress=[], callType=call). Формула dune_adj_old ошибочно предполагала, что reth их не трейсит.

**Правильная формула dune_adj:**
```sql
dune_adj_true = all traces
              − suicide
              − 0x100 calls (block_number >= Pectra_block)
-- НЕ удалять 0x01–0x0a, так как reth их тоже трейсит
```

**Итог: +866 и +301 — это артефакт формулы dune_adj_old, не потеря данных. BC точно соответствует reth. Верифицировано на уровне блоков.**

### [2026-07-18] Расследование reth_specific_M10=57,137 — что трейсит reth но не Erigon в блоках 10M–11M

**Запрос:** разберём M10=57,137 — что трейсит reth но не Erigon в блоках 10M–11M.

**Root cause: CALL-to-EOA traces (call к адресам без bytecode).**

Erigon (Parity trace format) **не записывает** CALL-трейсы к EOA-адресам (addresses without code).
Reth (Geth debug_traceBlock) записывает **все** EVM CALL frames, включая к EOA.

**Drill-down:**
- Per-1000: спайк в 10,365,000–10,369,999 = 9,391 reth_specific (16.4% от 57,137)
- Per-10: максимальный пик в 10,366,000–10,366,009 (172 reth_specific)
- Блок 10,366,004: BC=237, Erigon=200 → **37 reth_specific** (прямое расхождение, dune_specific=0)
- Scylla: 41 tx с 2 трейсами; Erigon: только 4 tx с 2 трейсами → **37 tx имеют extra trace в reth**
- Контракт `0x98ad263a95f1ab1abff41f4d44b07c3240251a0a`: withdrawal-контракт, получает вызов от EOA,
  делает callback-CALL с 0.09 ETH обратно вызывающему EOA → reth фиксирует этот sub-call, Erigon нет.
- 38 из 41 двутрейсовых tx → 0x98ad263a; 3 другие → иные контракты с тем же паттерном (EOA callback)
- Адреса-получатели callback (0xb4f517af, 0x167eea6b, 0x008b244d) — 0 CREATE traces в Erigon → подтверждены как EOA

**Итог M10=57,137:**
- Спайк 10,365M–10,369M: 9,391 (от активного использования 0x98ad263a)
- Остальные ~47,746 — тот же механизм (CALL-to-EOA) в других блоках M10, рассредоточенный

**Механизм расхождения форматов:**
```
tx:  EOA → 0x98ad263a → CALL(value=0.09ETH) → EOA (callback)

Reth:   2 трейса (root call + sub-call к EOA)
reth_specific = sub-call к EOA, который Erigon скипает
```

### [2026-07-24] Ревью аллокаторов v23 — диагностика OOM (предыдущая сессия)
Ответ: Корень OOM — worker OS-потоки (spawnHistoricalWorkers, 4 std.Thread.spawn) вызывают std.http.Client.fetch() с io_uring backend. Каждый HTTP-запрос из не-io_uring потока создаёт новый Fiber (~60 MB из GPA через PageAllocator.map → mmap). Созданные fibers уходят в per-thread free-queue io_uring потоков и НИКОГДА не используются повторно историческими worker OS-потоками. Итог: unbounded alloc 60 MB × каждый запрос. У v23 процесс дошёл до 241 GB RSS (4017 fibers × 60 MB), OOM kill. Процесс был убит (pkill с разрешения пользователя). Scylla и Postgres живы.

Дополнительно добавлены диагностические меры:
- v24: 64 MB cap на recvFrame() (защита от corrupt bodyLen → OOM)
- v25: timing instrumentation в CqlConn.init и HistoricalConns.open → подтверждено, что conns готовы за 57ms, OOM происходит ПОСЛЕ этого, в spawnHistoricalWorkers

Фикс (не реализован): заменить io_uring на blocking IO для FetchClient в workerEntry.
