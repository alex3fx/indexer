## Целостность данных — приоритет №1 (финансовая система)

**Это финансовая система.** Одна пропущенная транзакция или лог-событие может изменить решение,
принятое на основе этих данных. Поэтому:

- **Нулевая погрешность для целых чисел.** Счётчики строк, суммы, количества транзакций —
  всё целочисленное, погрешность недопустима. Float-поля (суммы ETH, цены газа) — только в
  пределах физической точности IEEE 754; округление и усечение при хранении недопустимы.
- **Полнота критична.** Отсутствие одной транзакции = неверный результат финансовой логики.
  "Статистическая погрешность 0.001%" — не существует в этом контексте. Любое расхождение
  с источником истины (Dune, on-chain данные) требует объяснения и устранения.
- **Ошибки чтения/записи Scylla** (таймауты, `Operation timed out`) — нормальная часть
  работы на таких объёмах, **всегда** обрабатывать через retry+backoff, не молча пропускать.
  Пропуск без retry = потеря данных.
- **Перед закрытием любой миграции** — независимая верификация (count/diff); read==written
  самого инструмента недостаточно, если внутри есть `continue`/skip на ошибках.

## Ключевые технические детали

### CQL Unprepared (0x2500) — исправлено
Scylla вытесняет cached prepared statements под нагрузкой. `batchSendRows(prep *Prepared, ...)` —
при `error.CqlUnprepared` делает re-PREPARE на том же соединении и повторяет. Верифицировано 3 дня.

### Throughput — что реально
Burst-тесты (< 1 мин, 100-2000 блоков) дают 40-983 blk/s — **не репрезентативны**: не успевают
столкнуться с compaction backpressure Scylla. Реальная sustained-скорость: ~49 blk/s для зоны
24M (confirmed 1-hour run), ~9.5 blk/s в near-head зоне (25.3M+, высокая плотность).

### Scylla на /storage
Данные пишутся на `/storage/scylla-eth` — выделенный LVM 20.96 TiB (не `/var/lib/docker/...`).
Свободно ~20 TB. Оценка на всю цепь: ~13.5 TB. Следить за диском с первого дня.

### contracts_by_address_v2 vs addresses_by_bytecode — ожидаемое расхождение
PK `contracts_by_address_v2` = `(address, block_number)` — один адрес, задеплоенный N раз, даёт
N строк. PK `addresses_by_bytecode` = `(hash, seq, bucket, address)` — одна строка на уникальную
(bytecode, address) пару независимо от числа деплоев. Разница ~32k — это CREATE2+selfdestruct
редеплои с тем же bytecode. Это не баг, а структурное свойство схемы.

### Ghost-строки в contracts_by_address_v2 — ОТКРЫТАЯ ПРОБЛЕМА

```
  tx_hash ≠ null (success):   102,759,056

  из них: редеплои одного адреса:   800,017  = 102,759,056 - 101,959,039
```

**Три категории расхождения:**

1. **Ghost-строки (102,640)** — `tx_hash = null`. Reverted CREATE2-деплои, snap-индексер
   заранее записал адрес, транзакция не прошла. Эти адреса не существуют на блокчейне.

2. **Редеплои одного адреса (800,017 extra строк)** — один адрес задеплоен N раз (CREATE2 +
   selfdestruct + CREATE2). Etherscan считает уникальные адреса, мы храним каждое событие деплоя.
   Также сюда входят строки "failed attempt + later success": тот же CREATE2-адрес был
   попытан в неуспешной транзакции, потом задеплоен успешно (пример: 0x3ae7942742939fe9bd1b5145812e2a3a37c3e744).
   **Это структурно корректно** — PK (address, block_number) позволяет N строк на адрес.

3. **Фантомные уникальные адреса (137,145)** — адреса с tx_hash ≠ null, но из **failed
   транзакций** (status=0), и никогда не задеплоенные успешно. Trace API (Erigon) возвращает
   `result.address` даже когда outer tx ревертится, наш трансформер не фильтрует по статусу.
   Эти адреса не существуют на mainnet. Примеры: `0xfdb5e022401566c50ce41ba6509976c7e92f315d`
   (block 6468169), `0x5fc643ee1745e44f5f7dcc6aadb1d36abfd72e9b` (block 6659527).
   ~0.26% всех строк с tx_hash приходят из failed txs (sample из 9,900 строк, tool: `check_tx_status/`).

**Корень проблемы**: трансформер (`src/pipeline/transformer.zig`) не проверяет `txRow.status`
при записи контрактов. Trace API Erigon возвращает `result.address` для CREATE-фреймов даже
когда tx ревертится (вся state-машина откатывается, но trace записывает что было исполнено).

**Правило:** после каждого запроса пользователя и завершённого ответа — добавлять запись в
`CONVERSATION.md` в корне репозитория. Формат:

```
### [дата время] Запрос пользователя (дословно или краткий пересказ)
Ответ: [финальный вывод без промежуточных рассуждений — только результат/цифры/вывод]
```

Копировать именно **финальные** результаты из консоли, не объяснения процесса. Промежуточные
"проверяю...", "читаю файл...", "запускаю..." — не пишем. Только то, что пользователь видит
как результат работы.

## Кэш Dune-запросов в Obsidian

**Правило:** любой Dune Analytics запрос (новый или повторный) — сохранять в
`/home/alex/Obsidian/DevVault/01-Projects/Lotos/task1/ETH_ERC20_DUNE_SCYLLA_QUERY_CACHE.md`.

Что сохранять:
- Query ID (Dune query number) и Execution ID
- SQL запроса (полностью)
- Итоговые числа / ключевые строки из результата
- Стоимость (кредиты) если показана
- Дату выполнения

Зачем: Dune-запросы платные (≈14 кредитов каждый), повторное выполнение тех же запросов
бессмысленно. Перед созданием нового запроса — сверяться с кэшем. Если тот же вопрос уже
был, брать готовый query ID через `executeQueryById`, не делать новый.

