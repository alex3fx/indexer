## Что было сделано в этой сессии

### 1. Перенос ScyllaDB с Docker на native (решён bottleneck)
- Старый Docker Scylla: smp=2, memory=4G, Docker Desktop I/O (1100 IOPS / 4.5 MB/s)
- Новый native Scylla: smp=24, native ext4, 86 MB/s direct write

### 2. Параметризация zigtest2 (build options)
Файлы: `zigtest2/build.zig`, `zigtest2/src/db.zig`

```bash
# Сборка
ZIG=/home/alex/lotos/zig-x86_64-linux-0.17.0-dev.263+0add2dfc4/zig
$ZIG build -Doptimize=ReleaseFast -Dpool-size=24 -Dpipeline=256
```

SPLIT для pool=24: 1+3+5+13+1+1 (blocks+txs+logs+itxs+contracts+cba)

### 3. Dump mode для zigtest2
Добавлена функция `dumpBatch` в db.zig + `DUMP_FILE` env var в main.zig.

**Формат дампа:**
- Magic: `ZIG2D\x01` (6 байт)  
- Batch header: `0xFF 0x00 [batch_id:4BE] [total_rows:4BE]` (10 байт)
- Row: `[table_id:1] [n_values:2BE] [values_len:4BE] [values_bytes]`
- table_id: 0=blocks 1=txs 2=logs 3=itxs 4=contracts 5=cba

**Генерация дампа:**
```bash
python3 -c "
import socket; key = b'LATEST_PROCESSED_BLOCK_NUMBER'; val = b'25078196'
s = socket.socket(); s.connect(('127.0.0.1', 6379))
def cmd(*p): c=f'*{len(p)}\r\n'.encode(); [c:=c+f'\${len(p[i])}\r\n'.encode()+p[i]+b'\r\n' for i in range(len(p))]; s.sendall(c); return s.recv(256)
cmd(b'AUTH',b'mockpass'); cmd(b'SET',key,val); s.close()
" && \
SCYLLA_DB_CONTACT_POINTS='["172.31.208.104:9142"]' \
SCYLLA_DB_KEYSPACE=eth SCYLLA_DB_CREDENTIALS='{"username":"cassandra","password":"cassandra"}' \
CM_CONNECTION_URL="redis://:mockpass@127.0.0.1:6379/0" \
RPC_URL=http://127.0.0.1:8545 CHAIN_ID=1 RAW_CHUNK_SIZE=1000 \
TO_BLOCK=25079196 BATCH_SIZE=10 \
DUMP_FILE=/home/alex/lotos/task1/gotest/writetest/dump_1000.bin \
./zig-out/bin/zigparser2
```

**Готовый дамп:** `/home/alex/lotos/task1/gotest/writetest/dump_1000.bin` (1.3 GB)
- 100 batches, 3,197,632 rows
- chunk_size=1000, 2 unique chunks (25078 и 25079)

### 4. Go loader (`gotest/loader/main.go`)
Читает дамп и загружает в ScyllaDB через raw CQL TCP (без gocql).

```bash
cd /home/alex/lotos/task1/gotest/loader
./loader -dump=../writetest/dump_1000.bin -host=172.31.208.104:9142 -conns=4 -pipe=64
# sweep: -conns=0 проверяет 1,2,3,4,6,8 conns/table
```

**Результаты loader sweep (smp=24 ext4 8GB):**
| conns/table | pipe | ms/block | rows/s |
|-------------|------|----------|--------|
| 4 | 64 | 25ms | 128k |
| 8 | 64 | 25ms | 125k |
| 12 | 64 | 25ms | 128k |

## Ключевые выводы

### ГЛАВНАЯ ПРОБЛЕМА: Partition key = chunk = block_number / 1000
- 1000 блоков → только **2 уникальных chunk** → только **2 из 24 шардов активны**
- Именно поэтому smp=24 не даёт преимущества над smp=2!

### Результаты бенчмарков (1000 блоков, ~3.2M строк)

| Конфиг | ms/block | rows/s |
|--------|----------|--------|
| Baseline (Docker smp=2, pool=32, pipe=256) | 21.6ms | - |
| Native smp=24 ext4 8GB, pool=24 pipe=256 | **21.7ms** | 148k |
| Native smp=24 ext4 8GB, pool=32 pipe=256 | 24.6ms | - |
| Go loader, smp=24 ext4 8GB, 4 conns/table | 25ms | 128k |
| smp=2 tmpfs 4GB, Go loader 12 conns/table | 25ms | 128k |

**Вывод**: ~25ms/block = максимум для 2 активных шардов (1000 блоков/chunk_size=1000).

### Продакшн конфиг (из ../input):
- ScyllaDB: smp=32, memory=128GB (4GB/shard!)
- При параллельной обработке тысяч чанков: все 32 шарда активны

### Для достижения 5ms/block нужно:
1. **Либо** уменьшить chunk_size до 50 (21 активных шарда) — но только при достаточной памяти (≥2GB/shard = 42GB total)
2. **Либо** обрабатывать несколько disjoint chunk-диапазонов параллельно  
3. **Либо** использовать машину с большим RAM для Scylla (128GB как в проде)

### Disk I/O:
- ext4 direct write: 86 MB/s (WSL2 VHD overhead)
- ext4 buffered: 3.3 GB/s (page cache)
- tmpfs /dev/shm: 1.2 GB/s sequential
- tmpfs commitlog НЕ помогает (CPU compaction становится bottleneck)
- tmpfs data dir = примерно то же что ext4 при одинаковом smp

## Следующие шаги для 5ms/block

1. Увеличить Scylla memory до 32-64GB (позволит smp=24 с 1.3-2.7 GB/shard)
2. Тестировать с ПАРАЛЛЕЛЬНОЙ загрузкой нескольких chunk-диапазонов
3. Или изменить chunk_size с 1000 на 50-100 при достаточной памяти

## Addendum — verification in current Codex session

- `../input` relative to `task1` does not exist; production files used here are under `task1/input/...`.
- Production compose in `input/@alexey_smolyakov/infrastructure/scylladb/compose.yml` is `--smp 32 --memory 128G`.
- Current native service on `172.31.208.104:9142` runs with `/etc/scylla.d/memory.conf`: `--memory=8G`; no explicit `--smp`, so it uses available CPUs.
- `/dev/shm/scylla` was being created by a systemd drop-in, but native service data/commitlog were still ordinary `/var/lib/scylla/...` directories, not tmpfs.
- `gotest/loader` had two measurement bugs:
  - It counted sent rows as written even when CQL returned `OP_ERROR`.
  - It reused prepared statement IDs from one connection on other connections. Prepared statements must be prepared on each worker connection/shard.
- Loader was fixed to:
  - Check CQL errors and print the first error.
  - Prepare the INSERT statement on every worker connection.
  - Support `-truncate` outside measured `elapsed`.
  - Print dump table counts and unique raw `chunk` keys.
- Dump verification:
  - `dump_1000.bin`: 3,197,632 rows, 100 batches, raw tables have only 2 chunk keys: `25078`, `25079`.
  - `dump_1000_chunk50.bin`: same rows, raw tables have 21 chunk keys.
- Important schema mismatch:
  - `input/.../raw/transactions.sql` and `input/.../raw/internal_transactions.sql` define `value bigint`.
  - Current working schema and `mocknode/sql/...` define `value varint`.
  - Zig/Go dump encoder writes `value` as CQL varint. Loading that dump into the `input` schema fails with `LongType: got 1 bytes`.
- Clean loader measurements after fixes:
  - Native ext4 service, `dump_1000.bin`, `conns=8 pipe=64`: `28.00 ms/block`, no CQL errors.
  - Native ext4 service, `dump_1000.bin`, `conns=12 pipe=128`: `26.49 ms/block`, no CQL errors.
  - Temporary user-run tmpfs Scylla on `127.0.0.1:9242`, `--smp=2 --memory=8G`, `dump_1000.bin`, `conns=8 pipe=64`: `28.03 ms/block`, no CQL errors.
  - Same tmpfs Scylla, `conns=12 pipe=128`: `26.53 ms/block`, no CQL errors.
- Conclusion from tmpfs test: tmpfs does not materially improve this 1000-block loader workload. The bottleneck is not raw disk bandwidth in this setup; the dominant limit is Scylla write/compaction CPU plus only two hot raw-table partition keys for `RAW_CHUNK_SIZE=1000`.
